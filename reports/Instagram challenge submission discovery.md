# Caption mentions require Meta's advanced access

Challenge Curator's preferred participation flow — a normal Instagram post or Reel with `@organizer` in the caption plus a challenge hashtag and a daily hashtag — **is not technically broken; it is access-gated.** Across the entire 2026 Instagram Platform API surface there is no mechanism that lets an app pull a list of "posts that recently mentioned `@organizer`" without already holding a media ID (confirmed current Meta documentation), and the two production-grade paths that could get an app a media ID without the organizer or Challenge Curator already knowing it — a caption-mention webhook, and hashtag-search polling — are each gated behind a named Meta review process (**Advanced Access** for the mentions/comments permission family, and the separately-reviewed **"Instagram Public Content Access" feature** for hashtag search), not behind any documented technical limitation of the mechanisms themselves. Our own spike confirms this pattern empirically rather than just in documentation: `ig_hashtag_search` returned an explicit, named HTTP 400 naming "Instagram Public Content Access" as requiring Facebook's review (our own empirical spike finding), while the two caption-mention webhook tests (Instagram Login's `comments` field and Facebook Login's dedicated `mentions` field) returned silent nulls that are equally consistent with "Standard Access doesn't deliver events from non-role-holder participants" and with "the mechanism itself doesn't fire for a pure caption mention" — the spike cannot yet distinguish these two explanations (our own empirical spike finding, cause not isolated). Native Tag People polling via `/tags` is the only mechanism confirmed to work under Standard Access with zero review, but it demonstrably does not surface caption-only mentions, so it cannot replace the preferred flow — only supplement it. Five researched commercial competitors (Easypromos, Woobox, ShortStack, Gleam, Brandwatch) show no evidence of bypassing this review gate; the consistent inferred pattern is that each vendor holds its own Advanced-Access-reviewed app and simply has organizers connect a Business/Creator account and Facebook Page to it. The recommendation that follows from this evidence is to pursue Meta App Review for both gates under a hybrid webhook-plus-hashtag architecture, not to weaken the participation mechanic — nothing in this research shows the preferred flow is unsupportable, only that it has not yet been tested with the access level production requires.

Source-type key used throughout, exactly as the research brief specifies: **[Meta-current]** = confirmed current Meta documentation (direct primary fetch unless otherwise flagged); **[Meta-current, unverified fetch]** = current Meta documentation whose specific page 404'd, redirected to stale/unrelated content, or was only available via an extraction tool rather than a clean raw fetch during this research — flagged inline every time it recurs, not just here; **[spike]** = our own empirical spike finding, drawn from `SPIKE-RESULTS.md`/`DECISION.md`; **[deprecated]** = old/deprecated Meta documentation; **[third-party]** = third-party or vendor documentation; **[inference]** = inference/hypothesis, never asserted as fact.

## 1. Executive conclusion

**Yes, the preferred flow is achievable — but only in production, and only after Meta App Review.** No official mechanism today lets Challenge Curator discover an unknown caption-mention post by enumeration; every mention-related edge is either a one-shot lookup requiring an already-known ID, or a webhook push that cannot be replayed or backfilled [Meta-current]. The two paths capable of supplying that first unknown ID without a pre-existing list — a `mentions`/`comments` webhook, and hashtag-search polling — both exist and are both documented as functioning mechanisms, but both are gated: webhook delivery to non-role-holder public participants requires **Advanced Access** to the `instagram_manage_comments`/`instagram_business_manage_comments` permission family, and hashtag search requires the separately-named **"Instagram Public Content Access"** feature, confirmed directly by our own spike's HTTP 400 ("To use 'Instagram Public Content Access', your use of this endpoint must be reviewed and approved by Facebook") [spike]. Both gates require Business Verification and formal App Review [Meta-current]. Neither gate has anything to do with whether caption @mentions or hashtags work as a concept — Meta's own `ig_hashtag_search` and `mentions` documentation describe exactly the behavior Challenge Curator needs; the blocker is authorization tier, not capability.

## 2. Official Meta discovery-mechanism map

Every mechanism on the current Instagram Platform surface that could plausibly feed Challenge Curator a candidate submission is inventoried below, with a strict DISCOVERY/LOOKUP classification per the task's own definitions (DISCOVERY = can return media IDs not already known; LOOKUP = can only retrieve data once a media ID/comment ID is already supplied). Webhooks are their own third category — a **push**, not an enumerable list — and are called out as such rather than forced into either bucket.

**`comments` webhook (Instagram API with Instagram Login, host `graph.instagram.com`)** — **PUSH, not enumerable.** Mentions are folded into this field rather than independently subscribable; Meta's own field table describes mentions for this product as "Included in the `comments` webhook notification" [Meta-current]. The documented payload (`id`, `from{id, username}`, `text`, `media{id, media_product_type}`, `parent_id`) has no flag distinguishing an ordinary reply comment from a mention [Meta-current, content retrieved via extraction tool rather than a raw-HTML fetch — treat exact wording as a close paraphrase]. Required permissions: `instagram_business_basic`, `instagram_business_manage_comments` [Meta-current].

**`mentions` webhook (Instagram API with Facebook Login / general Graph API Webhooks "Instagram" object, host `graph.facebook.com`)** — **PUSH, not enumerable**, but structurally richer: it is an independently subscribable field with a documented payload of `{media_id, comment_id}`, and it explicitly distinguishes "Mentions on Media" (caption-only, `comment_id` absent) from "Mentions on Comments" (both IDs present) [Meta-current]. Required permission family: `instagram_manage_comments` [Meta-current, unverified fetch — direct WebFetch of the exact permission reference page redirected into unrelated Threads-permission content during this research; the permission name is corroborated via search-snippet and the IG User edges table, not a clean re-verified primary fetch].

**`mentioned_media` edge** — **LOOKUP.** `GET /{ig-user-id}?fields=mentioned_media.media_id({media_id}){...}` requires a known `media_id` and cannot enumerate [Meta-current]. Confirmed empirically to work perfectly once an ID is supplied [spike].

**`mentioned_comment` edge** — **LOOKUP.** Same pattern, keyed by `comment_id` [Meta-current, unverified fetch — the canonical `/docs/instagram-api/reference/user/mentioned_comment` URL 404'd during this research; existence and parameter shape corroborated via the IG User edges reference table and secondary synthesis, not a direct clean fetch].

**`POST /{IG_USER_ID}/mentions`** — **Write-only, N/A to discovery in either direction.** Creates a reply comment; it is not a read mechanism at all [Meta-current].

**`/tags` edge (`GET /{ig-user-id}/tags`)** — **DISCOVERY**, the one genuine enumerable list edge for anything mention/tag-adjacent — but it covers native "Tag People" tagging only, never caption @mentions [Meta-current]; confirmed empirically both ways in the spike (native tag discoverable, caption-only mention absent) [spike].

**Business Discovery (`{ig-user-id}?fields=business_discovery.username({target})`)** — **LOOKUP by known username, of the target's own content** — not a mentions mechanism at all. It returns a *named* public Business/Creator account's own profile and own media, never third-party posts that mention that account [Meta-current]. It could theoretically be abused as a closed-roster scraping technique (see Architecture G, §9), but that is LOOKUP-of-knowns, never DISCOVERY-of-unknowns, and personal (non-professional) participant accounts are categorically excluded from it [Meta-current, unverified fetch — the legacy `/docs/instagram-api/business-discovery` URL 404'd; content corroborated via the IG User edges reference table].

**`ig_hashtag_search` → `{hashtag-id}/recent_media` / `top_media`** — **DISCOVERY**, genuinely enumerates unknown media, but indexed by hashtag, never by @mention [Meta-current]. Gated behind "Instagram Public Content Access," confirmed directly by our own spike's HTTP 400 [spike] — see §4 and §6.

**Instagram Basic Display API** — **Dead.** End-of-life December 4, 2024; was the only path that ever touched personal (non-professional) accounts directly, and is not usable for any 2026 architecture [third-party, TechCrunch, corroborated by Meta's own changelog research finding no newer replacement].

**Activity/notification history ("You" tab)** — **No third-party API equivalent exists at all.** This is a first-party-only surface; there is no endpoint to retroactively pull a user's own historical mention/tag notifications predating a webhook subscription [Meta-current, by documented absence rather than an explicit denial — no retention duration is documented either].

No 2025–2026 Graph API changelog entry introduces a mentions-listing, mentions-search, or activity-log capability beyond what's catalogued above; the changelog research surfaced only the Basic Display API shutdown, Insights metric deprecations, and Direct messaging feature additions in that window [Meta-current, sampled search of `developers.facebook.com/docs/graph-api/changelog/`, not an exhaustive version-by-version review — flagged as a genuine gap in §10].

## 5. Pull-based mention investigation

The brief asks this question in exactly these terms: is there any official mechanism that lets an authorized app periodically ask, in effect, "give me posts that recently mentioned `@the_calligrail`," without the app already knowing the media IDs? The documented, Meta-sanctioned workflow for mentions is unambiguous and was checked directly against Meta's own Mentions guide: **webhook push → extract `media_id`/`comment_id` from the payload → `mentioned_media`/`mentioned_comment` lookup using that ID** [Meta-current]. No step in that documented flow involves listing, searching, or paginating over mentions by account; the ID must originate from a webhook event, full stop. The only genuinely enumerable account-level list edge anywhere in the IG User reference tree, `/tags`, is explicitly scoped to native tagging and is documented as a separate concept from caption/comment @mentions [Meta-current]. A sampled review of the 2025–2026 Graph API changelog (not an exhaustive version-by-version pass — flagged as a gap in §10) surfaced no new mentions-listing, mentions-search, or activity-log feature in that window [Meta-current].

The absence of this capability, combined with the webhook-first design documented across both login products, reads as a deliberate Meta product choice rather than an oversight: mentions are meant to be consumed in real time as they occur, not reconstructed after the fact [inference]. The practical consequence for Challenge Curator is severe if taken at face value — if a webhook subscription is not active, or a delivery is dropped, at the exact moment a submission post goes up, **there is no official retry or backfill mechanism for that specific mention** anywhere in the documented API surface [Meta-current, by absence]. This is corroborated independently by Easypromos's own help documentation, which states plainly that "the Instagram API does not allow retroactive searches" and that past posts are never imported retroactively [third-party, Easypromos help center] — a vendor operating at commercial scale confirming the same structural ceiling from the outside.

**Explicit answer, as the brief requires: No.** Caption mentions cannot currently be pulled or polled as a list through any official Meta API. What the API exposes instead is exactly two things: a webhook push (real-time only, not replayable, access-tier-gated for non-role-holder participants) and an ID-keyed lookup (`mentioned_media`/`mentioned_comment`, confirmed working perfectly once an ID exists [spike], but incapable of producing that ID itself). This is a confirmed structural fact of the current API surface [Meta-current], not an inference — though whether Advanced Access changes the webhook's *delivery reliability* for the caption-only case specifically remains untested [spike, unresolved].

## 6. Hashtag-polling feasibility analysis

Technical possibility and production reliability are different questions, and Meta's own documentation — once read past the access gate — answers the reliability question with real caution, not reassurance. Four documented constraints stack against completeness: `recent_media` caps at **50 results per page** and documents only a forward-only "after" cursor, explicitly stating "a before cursor will not be included" [Meta-current]; the edge "only returns media objects published within 24 hours of query execution" [Meta-current, direct quote]; Meta explicitly disclaims strict ordering — "Responses will not always be in chronological order" [Meta-current, direct quote]; and there is no documented statement of a total-results cap distinct from the per-page limit, meaning what happens to the 51st-and-beyond qualifying post within a 24-hour window is simply undocumented [Meta-current, by absence]. This is a meaningfully weaker pagination contract than ordinary Graph API paging, and it closely echoes — though is not textually identical to — the exact failure the spike already observed on the sibling `/tags` edge, which returned no `paging` object at all despite Meta's own docs describing cursor support for it [spike]. `top_media` avoids the 24-hour cutoff but trades it for engagement-ranking rather than exhaustiveness, so a low-engagement submission is not guaranteed to appear there either [Meta-current].

Mapped against the specific volumes the brief asks about: at roughly **20 submissions/day**, a single `recent_media` page (50/result cap) comfortably covers the full 24-hour window even with uneven arrival timing, making completeness plausible if polled at least once per 24 hours — though "not always chronological" means even this volume cannot be assumed gap-free without an independent reconciliation check [inference]. At **50/day**, volume sits right at the single-page boundary; any clustering of posts within the day could push the true count above 50 within the rolling 24-hour window, at which point the forward-only, non-chronological cursor's actual behavior in production is simply unverified [inference — no live test of this specific edge exists anywhere in this research, blocked by the access gate itself]. At **200/day**, a poller would need multiple pages per 24-hour cycle, and the combination of non-chronological ordering with an "after only" cursor creates a real, documented-constraint-driven risk that a given post's position in the result set is unstable across polls — a post visible on page 2 at time T could be excluded or re-positioned by time T+1 [inference, built from stacked documented constraints, not a single Meta statement]. At **500/day**, this risk compounds further and there is, per this research, **no documentation and no community report either confirming or refuting** whether a post can be silently dropped from the retrievable window before a later poll — this is explicitly the single most important unresolved empirical question for the feasibility decision, and it remains untested specifically because Test E was blocked by the Public Content Access gate before it could reach this question [spike + Meta-current gap, both confirmed].

One piece of good news: the 30-unique-hashtags-per-7-day-rolling-window cap [Meta-current, confirmed on all three hashtag endpoints' reference pages] does **not** bind Challenge Curator's actual design of one persistent challenge hashtag plus one new daily sub-hashtag. A strict reading (poll each day's sub-hashtag only while it's current) uses at most 8 unique hashtags in any rolling week — far under the cap; the cap would only become binding under a design that insists on indefinitely re-polling every sub-hashtag ever introduced across a ~30-day campaign, which is not how a "daily hashtag" naturally needs to be used [inference/computation, worked through explicitly in the access-requirements research]. Separately, no technical blog, developer-forum thread, or community report specifically describing `recent_media` completeness problems in production was found anywhere in this research — but this absence is explicitly flagged as "no evidence either way," not "confirmed reliable," since the use case (Advanced-Access-gated hashtag monitoring) is itself rare enough among public developer complaints that absence of complaints carries little weight [Meta-current gap, explicitly not overclaimed]. A related, separately-sourced signal: Instagram's own consumer app has reportedly been phasing out its chronological "Recent" hashtag tab in favor of "Top"/"Reels" surfacing for some users [third-party, Gulf News — about the consumer app UI, explicitly not the same system as the Graph API edge, and this distinction must not be blurred].

**Verdict on completeness, not just possibility:** hashtag polling is a real, working DISCOVERY mechanism once access is granted, but it is not, by itself, a documented-complete mechanism at any volume this research can confirm — its own documentation builds in non-determinism (ordering), a hard recency ceiling (24 hours), a weak pagination contract (forward-only, 50/page, no stated total cap), and zero evidence either way about high-volume drop behavior. This is why §9's Architecture C treats hashtag polling as a reconciliation layer behind a faster primary signal, not as a sole production mechanism.

## 7. Commercial competitor implementation evidence

**Easypromos** is the clearest documented case and the most directly comparable to Challenge Curator's model: participants post to the main feed (Stories excluded) with both an @mention and the campaign hashtag present at publish time, from a public account — personal accounts are explicitly accepted on the participant side [third-party, Easypromos help center]. The organizer side requires "an Instagram business account" connected to the Facebook Page that manages it [third-party] — directly consistent with Meta's own documented prerequisite for the `mentioned_media`/hashtag edges requiring `graph.facebook.com` and a linked Page. Easypromos states it "uses Meta's official API" and that "Meta verifies Easypromos for legal compliance annually" [third-party, vendor claim], and documents real completeness limitations that mirror exactly the structural ceilings found in Meta's own docs: no retroactive search ("the Instagram API does not allow retroactive searches"), no detection of mentions/hashtags added via a post-publish caption edit, and private profiles must fall back to a manual web-form submission [third-party, vendor claim]. The most plausible reading consistent with every Meta-documented constraint in this report is that Easypromos operates one (or a small number of) Meta app(s) that has already cleared Advanced Access/App Review once at the vendor level, and each customer's Facebook Login + Page connection simply supplies the authorized IG User context that app needs [inference/hypothesis — not confirmed by any Easypromos-published architecture diagram or Meta partner-directory listing found in this research].

**Woobox** and **ShortStack** show the same pattern from the hashtag side specifically: both explicitly require the organizer to hold an Instagram Business Profile linked to a Facebook Page before any hashtag feed can be created [third-party, vendor help centers for both], and both describe a lookback-plus-ongoing-collection model ("previous 24 hours and throughout the campaign's Entry period" for Woobox) that lines up closely with `recent_media`'s own documented 24-hour window [third-party, with the match to the Meta edge flagged as inference, not a vendor-confirmed architecture statement]. Neither vendor is documented as supporting @mention-based collection at all — both are hashtag-only [third-party]. **Gleam** is the one vendor that directly and explicitly attributes a capability change to a Meta policy shift, stating that "due to Instagram's new API limitations, Gleam is no longer able to support certain Instagram actions like the 'Like a Photo/Video' action" [third-party, vendor-published] — useful corroborating evidence that these vendors genuinely operate inside Meta's actual constraints rather than around them. Gleam also frames @mention-based import as "now the preferred method over hashtags" for visibility into entrant usernames and timestamps, requiring an Instagram Business Profile [third-party].

**Brandwatch** is the most transparent of the six about a historical Meta-driven capability loss: it confirms per-customer OAuth-style authentication against Instagram's official API, states it "can still gather all of your owned posts" and "we are still able to gather all posts for hashtags" for connected/owned channels, but explicitly lost the ability to receive data for non-owned channels (competitors, influencers) after Instagram's 2018 policy changes, with no expectation that capability returns [third-party, vendor blog — dated to the original 2018 announcement window, with no 2024–2026 reconfirmation found, flagged as a currency gap]. Brandwatch's documented capability is scoped per-connected-account, not a broad cross-account firehose — the most explicit rejection, among the six vendors researched, of any special "listen to anyone's hashtag/mention activity at scale" tier beyond the standard per-customer OAuth model.

**Mention.com** is the clear outlier: its public marketing claims a "Media Monitoring API" with "real-time" Instagram coverage [third-party, vendor marketing], but no primary documentation describing the exact Instagram endpoint, access tier, account-type requirement, or real-time-vs-polling behavior could be located anywhere in this research — the specific product page attempted returned a 404. Given the severity of Instagram's 2018–2020 third-party lockdowns on public-content access, it is plausible that Mention.com's current Instagram capability is materially reduced from its original design, or routed through a different/degraded data layer entirely [inference/hypothesis, explicitly unconfirmed — this is the single largest unresolved question in the whole commercial-precedent track and should not be treated as settled either way].

Across every vendor with enough documentation to assess ( Easypromos, Woobox, ShortStack), the one consistent, repeated pattern is: **the organizer/brand must hold a Business or Creator Instagram account connected to a Facebook Page; the participant can remain an ordinary public personal account** [third-party, consistent across all three]. No vendor in this set visibly displays a "Meta Business Partner" badge or discloses its specific Advanced Access/App Review status beyond Easypromos's general "Meta verifies us" claim [third-party, with the "Meta Verified Tech Provider" label specifically flagged as an unconfirmed search-synthesis claim, not a primary-source badge]. No vendor among the six was found to be using direct, un-gated web scraping instead of the official API [absence of evidence, not confirmation of absence].

## 8. Instagram UI vs third-party API comparison

| Human Instagram workflow | Closest third-party API equivalent | Access gate | Gap vs. the human experience |
|---|---|---|---|
| See that someone mentioned me (caption) | Webhook `mentions`/`comments` field fires → `mentioned_media` by ID | Advanced Access for non-role-holder triggers (theorized) | No bulk "list all my mentions" call exists at any access tier [Meta-current] |
| See that someone mentioned me (comment) | Same webhook → `mentioned_comment` by ID | Same, plus explicitly excluded for private-account or Story mentions [Meta-current] | Same ID-dependency; also excluded on Stories entirely |
| Open "Tagged"/"Photos of You" | `GET /{ig-user-id}/tags` | **Standard Access — confirmed sufficient, no review needed** [spike] | Closest 1:1 match of any workflow examined, but excludes private media and reflects only what's tagged, not approval-queue state |
| Search/browse `#challenge` (Top + Recent, no stated cutoff) | `ig_hashtag_search` → `top_media`/`recent_media` | **"Instagram Public Content Access" — confirmed required, confirmed blocked under Standard Access** [spike + Meta-current] | `recent_media` capped at a 24-hour window and 50 results/page with non-chronological ordering; the in-app "Recent" tab has no such documented cutoff [Meta-current + third-party] |
| Open a known post by URL/ID | `mentioned_media`/`mentioned_comment` lookup | Standard Access sufficient for a role-holder's own account [spike] | Works perfectly once an ID exists — but an ID must come from somewhere else first |
| General free-text/keyword search | **No API equivalent exists at all** | N/A | The Graph API exposes no general search surface beyond hashtag-ID lookup; this is a first-party-only capability [Meta-current, by absence] |
| Scroll Activity/notification history for past mentions/tags | **No API equivalent exists at all** | N/A | No endpoint retrieves a user's historical notification log; no official retention window is even documented for the in-app version [Meta-current, by absence] |

The structural lesson is explicit, not incidental: Instagram's own first-party app is deliberately unrestricted in exactly the places the third-party API is quota- or time-boxed (hashtag recency, mention backfill, general search), and the one area where API parity is closest to the human experience — `/tags` — is precisely the one mechanism that does not cover Challenge Curator's actual caption-mention requirement [inference, built from the documented asymmetry across all three features examined, not a direct Meta statement of policy intent — no Meta source found in this research explicitly states this asymmetry is deliberate].

## 9. Candidate Challenge Curator architectures

| Architecture | Participant UX | Meta permission/review requirement | Reliability/completeness | Latency | Alpha suitability | Production suitability |
|---|---|---|---|---|---|---|

| **B.** Public Content Access hashtag polling | Ideal — same normal flow, directly uses the hashtag already required | "Instagram Public Content Access" feature, App Review, Business Verification; confirmed blocked even for the app's own role-holder account | Documented structural weaknesses (24h window, 50/page cap, forward-only non-chronological cursor, no total-cap statement); degrades with volume (§6) | Poll-interval bound, not real-time | **Cannot be validated at all pre-approval** — fully blocked, confirmed by direct HTTP 400 | Viable as a secondary/backstop layer; risky as a sole primary mechanism at realistic volumes |

A few dimensions are worth spelling out in prose because a table compresses them too much. **Technical dependencies and complexity** rise in a clean line from D (lowest — a single polling call, no webhook infra) through F (a URL-paste UI plus one lookup call) to A (webhook listener plus signature verification plus the ID-lookup chain) to B (cron infrastructure, pagination handling, and dedup state) to C (the union of A and B, including reconciliation logic to merge two independently-arriving signals for the same post) — with E notionally lowest in engineering complexity for Challenge Curator itself, since the hard problem is contracted away, but highest in hidden operational risk, since the entire discovery pipeline becomes dependent on a vendor whose own mechanism, pricing, and SLA were not confirmable anywhere in this research (§7). **Scale limits** separate the architectures sharply: A has no documented event-volume ceiling (the only unknown is whether it fires at all for the caption-only case); B is bounded by the 24-hour/50-per-page/non-chronological constraints detailed in §6, which bite harder as daily submission volume rises past roughly 50/day; D and G are bounded by human/roster labor costs that scale badly; F is the most labor-bound of all. **What remains unknown and what must be proven** for A and B both reduce to the same root question — does Advanced Access actually change the observed behavior — and §12 proposes the cheapest available test of that question before any App Review submission is made.

## 10. Remaining unknowns

Several of these recur from earlier sections and are restated here deliberately, per the brief's own instruction not to let caveats get buried in a single section. **Documentation-reliability gaps**: the `mentioned_comment` reference page, the legacy Business Discovery page, and the `instagram_manage_comments`/`instagram_business_manage_comments` permission pages all either 404'd or redirected to stale/unrelated content on direct fetch during this research and had to be corroborated via search-snippet synthesis or the IG User edges table instead [Meta-current, unverified fetch — flagged in §§2, 4]; the Instagram webhook fields/permissions matrix was retrieved via an extraction tool rather than a raw HTML view, so exact wording should be treated as a close paraphrase rather than a verbatim quote [Meta-current, unverified fetch]; the current Graph API version (one secondary aggregator claims v26.0, shipped July 29, 2026) was never confirmed against a primary Meta changelog page in this research pass [third-party, unconfirmed]. **Mechanism-level unknowns**: whether a pure caption-only mention (zero comment activity) actually fires Instagram Login's `comments` webhook field at all, independent of access tier, is not resolved by any primary source found [Meta-current, genuine ambiguity, not just an access question]; whether `recent_media` suffers the same "paging object silently absent despite documented cursor support" failure the spike directly observed on `/tags` is unknown, since no live test of `recent_media` exists anywhere in this research [spike precedent + untested extrapolation]; whether a post can be silently dropped from a high-volume hashtag's retrievable window before the next poll has no documentary or community evidence either way [Meta-current gap, explicitly the central open feasibility question per §6]; whether the 30-unique-hashtags/7-day cap is counted per IG User, per token, or per app is not stated explicitly on the primary pages fetched in this research [Meta-current, ambiguous counting unit]. **Access-level unknowns**: no single Meta page explicitly states that Standard Access is sufficient (or insufficient) for receiving mention-webhook events specifically — the Standard/Advanced theory for webhook delivery is corroborated-by-analogy from the hashtag endpoint's explicit rejection, not independently confirmed for webhooks in their own right [inference, not yet directly confirmed]; whether an approved "Instagram Public Content Access" grant is scoped by hashtag, campaign, or time once granted is undocumented — absence of restriction language is not the same as confirmed unlimited scope [Meta-current, flagged as an open gap rather than an assumption]. **Commercial unknowns**: Mention.com's actual current Instagram data-acquisition mechanism is entirely unconfirmed publicly [third-party, unresolved — the largest gap in the commercial-precedent track]; no vendor among the five with usable documentation discloses whether its App Review was done once at the vendor level or per customer [third-party, consistent with either model]. **Product-level unknowns**: the exact lookup mechanism (if any) for retrieving metadata from a bare organizer-pasted permalink/URL under Architecture F was not researched in this pass and should be treated as a genuine open question, not an assumed capability [inference, flagged explicitly].

## 11. Recommended next decision

**Do not change the participation mechanic.** Nothing in this research shows the preferred flow — normal post/Reel, caption @mention, challenge hashtag, daily hashtag — is unsupportable; it shows only that it has not yet been tested at the access tier production requires. Changing to require native Tag People now, on the strength of `/tags` being the only mechanism that currently works under Standard Access, would be optimizing for what's easy under the spike's current access level rather than what the evidence says is actually broken — and the evidence does not say that.

The recommended path is to **pursue Meta App Review for both gates simultaneously, under one Business Verification, targeting Architecture C (hybrid webhook-primary, hashtag-reconciliation-backstop) as the production design**: `instagram_manage_comments`/`instagram_business_manage_comments` Advanced Access (Facebook Login path preferred over Instagram Login, since it is the only one of the two with documentation explicitly confirming caption-only coverage via the "Mentions on Media" webhook sub-case), and the "Instagram Public Content Access" feature (needed regardless for the hashtag-reconciliation layer, and squarely inside Meta's own stated allowed-use category of "identify entrants to its contests, competitions, or sweepstakes" [Meta-current] — a genuinely positive approvability signal, not just a hopeful read). This recommendation is reinforced, not just assumed, by the commercial-precedent research: every vendor in the researched set with enough public documentation to assess (Easypromos, Woobox, ShortStack, Gleam, Brandwatch) shows the same inferred pattern — an organizer-side Business account plus linked Facebook Page, authenticated into a vendor app that itself appears to hold Advanced Access already — and none shows evidence of a way around Meta's review gate [inference, consistently corroborated across five independent vendors, §7]. App Review reads as the standard cost of entry for this entire product category, not an obstacle specific to Challenge Curator.

In the interim, **adopt Architecture F (manual/semi-manual URL import) as the Alpha-stage stopgap** while App Review is in flight — it requires no review, preserves the ideal participant-side UX completely, and only shifts friction to the organizer, which is an acceptable Alpha-stage trade given the alternative is no working discovery at all. **Layer Architecture D (`/tags` polling) as a zero-cost supplementary signal**, never a replacement — it costs nothing to keep running and will catch any participant who happens to also natively tag the organizer, but it is confirmed not to satisfy the caption-mention requirement on its own and must not be presented to the product team as a substitute for A/B/C.

## 12. Only then: the smallest next empirical tests

Before submitting anything to Meta App Review — a substantial undertaking involving Business Verification, a screencast of the live flow, and real review turnaround time, not a quick configuration change — two cheap, Standard-Access-only tests should be run first, because they bear directly on whether that investment is justified at all:

**Test 1 — isolate the webhook access-level hypothesis.** Add the existing Test C/D participant account as an Instagram Tester (an app role) and repeat the identical pure-caption-only-mention test on both Instagram Login's `comments` field and Facebook Login's dedicated `mentions` field, under current Standard Access, with zero code changes and zero App Review. This was already proposed in `DECISION.md` but not yet executed. If the webhook fires now that the participant holds a role, that cleanly isolates the Standard/Advanced access-role theory as the real cause of the earlier nulls — a strong predictor that Advanced Access will fix the production (arbitrary-public-participant) case, and a strong justification for proceeding with App Review. If it still does not fire, that points instead toward a genuine mechanism-coverage gap for caption-only mentions independent of access tier, which would need to be investigated before App Review is submitted rather than after.

**Test 2 — resolve the `/tags` pagination gap, at zero cost.** Manually call the identical `/tags` Graph API URL directly (via curl or a browser, not through the app) with an explicit `&limit=` parameter appended, using the existing token outside of chat. If more than the previously-observed 16 items return, the earlier view was silently truncated with no signal — a real reliability finding that affects Architecture D's viability even as a supplementary layer. If the same 16 items return, that is reasonably strong (not absolute) evidence the earlier result was already complete.

Neither test requires App Review, Business Verification, or any code change beyond what already exists, and both should be completed and their results folded back into `DECISION.md` before any App Review submission or further hashtag-volume testing is attempted — consistent with the original spike brief's own instruction not to propose further tests until the research itself was complete.
